# Architecture

## Frontend structure

The public frontend is intentionally small:

- [`frontend/index.html`](../frontend/index.html): neutral landing page for the portfolio repo
- [`frontend/trans.html`](../frontend/trans.html): main multilingual workflow demo
- [`frontend/script.js`](../frontend/script.js): vanilla JavaScript controller for the translation workflow
- [`frontend/emails-demo.html`](../frontend/emails-demo.html): optional secondary demo for framework-based email drafting

The frontend is static and can be served by any simple file server.

## Backend and API structure

The backend centers on two files:

- [`backend/app/main.py`](../backend/app/main.py): translation, rewrite, OCR, feedback, regeneration, variants, and export routes
- [`backend/app/api_emails.py`](../backend/app/api_emails.py): email drafting demo routes

Supporting utilities:

- [`backend/app/utils.py`](../backend/app/utils.py): moderation helper for critique safety
- [`backend/app/utils_pdf.py`](../backend/app/utils_pdf.py): direct PDF text extraction for text-based PDFs
- [`backend/app/db.py`](../backend/app/db.py): Postgres-compatible feedback persistence layer

## Request flow from UI to backend

### Translation workflow

1. The user enters text or uploads a file in `trans.html`.
2. `script.js` sends requests to the FastAPI backend through a runtime-configured backend URL.
3. The backend refines the English source and returns either:
   - translated output from `/full-process/`
   - rewritten English output from `/rephrase/`
4. The frontend renders the output and enables copy and feedback controls.

### Feedback and export workflow

1. The user saves a result as good or submits critique for regeneration.
2. Feedback rows are stored in a local SQLite database generated by the backend.
3. The frontend can fetch `/feedbacks/` to render history.
4. The frontend can call `/feedbacks/download` to export the saved rows as CSV.

## AI, translation, OCR, and content processing flow

### Translation flow

- The backend first rewrites the English source for clarity using the OpenAI API.
- It then translates that refined source.
- If a DeepL key is configured, DeepL is used first.
- If DeepL is not configured, the backend falls back to OpenAI-based translation.

### OCR flow

- Text-based PDFs are supported through direct extraction in `utils_pdf.py`.
- Scanned PDFs and image OCR are intentionally not enabled in the Phase 1 Vercel deployment.

### Regeneration flow

- A bad result can be critiqued through `/feedback/regenerate`.
- The backend moderates the critique, rewrites the source based on that critique, then translates again.
- The original bad feedback is still stored so the iteration path remains visible.

### Alternative outputs

- After a good result is saved, the frontend can request `/copy-variants/`.
- The backend generates multiple English alternatives and translates them into the selected target language.
- Each alternative can receive independent good/bad feedback.

## Honest limitations

- This public repo is a sanitized prototype-oriented portfolio copy, not the full original product.
- Feedback persistence is session-scoped through a frontend header and stored in a Postgres-compatible database.
- The frontend has no auth in this public version.
- The backend currently has no automated tests in this repo.
