# LexAi

LexAi is a sanitized portfolio project that demonstrates an AI-assisted multilingual content workflow. This public version focuses on the workflow itself rather than the original business website around it.

## Why I built it

I built LexAi to explore how a lightweight product experience could connect a frontend workflow to backend AI services for translation, rewriting, OCR-assisted intake, feedback collection, and output iteration.

## Project Evolution

LexAi started as a multilingual AI content workflow built around a real product need: helping users generate, translate, refine, and export content without manually moving between multiple tools. The early version included login and signup flows so user activity and usage could be tracked through accounts.

After testing the workflow, the requirement changed: users were less likely to try the tool if they had to create an account first. I redesigned the flow to remove the login barrier while still keeping user sessions separated. The updated approach used browser-side session tracking so each browser session could keep its own usage state, history, and token limits without mixing data across users.

The translation workflow also evolved through feedback. A “good” response could generate alternative variants, while a “bad” response asked for feedback and resent that context into the AI flow for regeneration. The goal was not just to translate text once, but to create an iterative content workflow where users could improve outputs, compare variants, reuse feedback, and export structured results.

This public version keeps the core workflow and removes private branding, deployment details, credentials, and third-party business context. It is intended to show the product and engineering decisions behind the prototype: simplifying user access, preserving session isolation, building feedback loops, supporting OCR/file input, and making AI outputs easier to review and export.

## Key features

- AI-assisted multilingual translation flow
- English rewrite/regeneration flow for prompt refinement
- Frontend to backend API integration
- OCR-based text extraction from PDFs and images
- Feedback capture and critique-driven regeneration
- Alternative output generation after a successful result
- Clipboard copy and CSV export for saved feedback history
- Optional email drafting demo as a secondary, self-contained example

## Tech stack

- Frontend: static HTML, CSS, vanilla JavaScript
- Backend: FastAPI
- AI: OpenAI API
- Translation: DeepL when configured, OpenAI fallback otherwise
- OCR: PyMuPDF for PDFs, Tesseract for images
- Persistence: local SQLite file generated by the backend for feedback history

## Workflow overview

The main workflow starts in [`frontend/trans.html`](frontend/trans.html), where a user can paste source text or upload a PDF/image for OCR extraction. The frontend calls the FastAPI backend in [`backend/app/main.py`](backend/app/main.py) to:

1. refine the English source
2. translate it into a selected language or rewrite it in English
3. save good or bad feedback
4. regenerate an output from critique
5. generate alternative outputs
6. export saved feedback as CSV

The optional email demo in [`frontend/emails-demo.html`](frontend/emails-demo.html) uses [`backend/app/api_emails.py`](backend/app/api_emails.py) to generate structured outreach drafts in several copywriting frameworks.

## AI, OCR, regeneration, and export flow

- Translation flow: source text is first rewritten for clarity, then translated.
- OCR flow: PDFs are parsed with text extraction and OCR fallback; images are processed with Tesseract OCR.
- Regeneration flow: a user can submit critique on a result, and the backend produces an improved English source plus a fresh translation.
- Alternative outputs: after saving a good result, the frontend can request multiple translated variants.
- Export flow: saved feedback rows can be downloaded as CSV for inspection.

## Run locally

### Backend

1. Create and activate a virtual environment.
2. Install dependencies:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

3. Copy the placeholder env file and fill in your own keys:

```bash
cp ../.env.example .env
```

4. Start the API:

```bash
uvicorn app.main:app --reload
```

The backend runs at `http://127.0.0.1:8000` by default.

### Frontend

Serve the `frontend/` folder with any simple static server. For example:

```bash
cd frontend
python3 -m http.server 5500
```

Then open:

- `http://127.0.0.1:5500/index.html`
- `http://127.0.0.1:5500/trans.html`
- `http://127.0.0.1:5500/emails-demo.html`

## Environment variables

Use placeholder values only.

```env
OPENAI_API_KEY=your_openai_api_key
OPENAI_MODEL=gpt-4.1-mini
ALLOWED_MODELS=gpt-4.1-mini,gpt-4o-mini,gpt-4o
DEEPL_API_KEY=your_optional_deepl_api_key

```

## Privacy and sanitization

This repo intentionally removes the original business website surface, login/signup flows, support flows, private domains, hosted API URLs, service-account files, local runtime artifacts, and deployment-specific details. It is presented as a portfolio proof-of-concept, not as a clone of any active commercial product.

## What I learned

- A small static frontend can still present a credible AI workflow when the API contract is clean.
- OCR and text processing are useful multipliers for translation workflows, but they require clear UX around extraction quality.
- Regeneration based on critique is often more persuasive in demos than one-shot generation because it shows iteration and control.
- Sanitizing a real project for public sharing takes deliberate separation of product logic from business-specific assets and operational details.

## Running Notes

The frontend is designed to run against the local FastAPI backend. The public repo does not include production deployment settings, API keys, or the original hosted environment. To test live AI calls, create a local `.env` file from `.env.example`, add valid API keys, start the backend with Uvicorn, and then serve the frontend locally.

Without API keys, the frontend and backend code can still be reviewed to understand the workflow structure, request flow, prompt/regeneration logic, OCR path, feedback handling, and CSV export behavior.
